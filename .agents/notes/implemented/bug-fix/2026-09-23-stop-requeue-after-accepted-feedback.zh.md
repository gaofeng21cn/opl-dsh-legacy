# Agent Note：传输接收通知后不再重复入队

Status: implemented

[English](2026-09-23-stop-requeue-after-accepted-feedback.md) | 中文

## 问题

Codex 队列命令成功退出时，通知可能仍在等待接收任务运行。若发送方因等待接收确认而重试，就会把同一通知再次入队，即使第一份已经排队，从而反复唤醒任务。

## 决策

`delivered` 对发送方调度而言是终态。传输拒绝仍保持 `enqueued`，并按有界封顶指数策略重试。传输成功接手后记录 `delivered` 且不设置重试时间；显式 `flush` 和 Host 恢复都不会再次发送。`received` 与 `consumed` 仍是接收方独立记录的事实；发送方不会把队列接收误报为目标已收到。

操作者停止会话时，仍在排队的自动续做由接收方一侧的收手撤回，这一行为由[结果边界记录](2026-09-23-control-recovery-outcome-boundaries.zh.md)负责，因此本条的发送方规则并不是阻止旧投递产生陈旧工作的唯一机制。交接后的恢复由接收方负责。接收方重启后读取持久 receipt 台账，并恢复所有未消费领取。outbox 记录创建前崩溃的情况仍由任务记录对账修复。

## 考虑过的替代方案

**持续重试直到收到确认。** 发送方无法区分仍在目标队列中的消息与目标丢失的消息，每次重试都会创建额外队列项。接收方已有持久恢复机制，因此发送方重试不能修复中断的审查。

**完全移除重试。** 进程启动失败或队列命令拒绝消息时，目标不会有任何副本。对此类明确的传输失败仍保留有界退避重试。

## 后果

传输接收后只唤醒目标一次，不再按确认间隔重复唤醒。若目标领取前已接受的消息后来丢失，发送方不会自动重试；部署必须保留已接收的队列项，或显式发起恢复。接收和消费仍可分别观测。
