# Agent Note：桌面任务通知与窗口关闭行为

Status: implemented

[English](2026-09-23-desktop-notifications-tray.md) | 中文

## 问题

桌面应用在关闭主窗口时退出，且不发出系统通知，因此用户切走后无法得知长任务已完成、失败，还是正在等待审批或回答。每次关闭也都是终结性的：无法在窗口让开的同时让运行中的 Host 继续存活。

## 决策

**通知由客户端上报、由 shell 呈现。** 应用渲染器本就收到通知所需的全部事实，而只有 Electron 主进程知道应用是否在前台。新的客户端插件（`packages/client/ui-desktop-notifications`）通过 preload 桥接上报四类事件：一次运行停止（`api-session/status` 由运行转为空闲的边沿）、一次运行失败（该会话运行期间的 `api-session/error`），以及有待处理的审批或回答（`uiSession.pendingInteractions`，即客户端自身可回答的暂停注册表）。shell 依据用户设置、前台抑制和已记住的上报标识集合决定是否通知。

运行结果带有按上报实例生成一次的标识，且会话离开注册表时不会重排其运行编号。运行编号由渲染器自己计数，因此若缺少实例部分，重新加载的渲染器会把首个观测到的运行重新编为 1，shell 就会把真实的完成当作重复而丢弃。待处理请求保留 Host 自己的请求键——它命名的是请求本身，而不是看到它的渲染器。子代理的结果属于父级回合，因此它的完成与失败都会被抑制；判定同时使用客户端会话列表与 Host 的 `api-session/added` 公告，后者正是识别不在当前导航链上的子代理的依据。

选择上报待交互注册表而非 `approval/request` 与 `user-questions/request` 瀑布，消除了对监听器顺序的依赖：认领请求的瀑布消费者不会调用 `next()`，因此其后的监听器永远看不到该请求。该注册表本身也按请求设键，因此替换请求会再次通知，而重复投递的请求不会。

**关闭窗口变为托盘决策。** 在 Windows 和 Linux 上，首次关闭会询问是收进托盘继续运行还是退出，并在用户勾选时记住答案，存入 `$DSH_HOME/desktop/desktop-preferences.json`（默认：通知开启、每次关闭都询问）。“收进托盘”既是默认项也是 Esc 对应项，因为隐藏窗口可以恢复，而退出应用不能。托盘可恢复并聚焦主窗口，并带有明确的“退出”菜单项；隐藏窗口永不停止 Host，而退出始终走既有退出路径——停止 Host、等待其子进程结束，现在还额外移除托盘图标。macOS 保持其平台行为；没有可用托盘图标的构建完全不拦截关闭。桌面环境拒绝创建托盘属于同一种情况：报告该失败并保留关闭的历史语义，而不是为了一处装饰让启动失败。

**shell 持有每个已发出的通知，直到它有了结果。** Electron 会回收只有发起调用局部变量引用的通知，而被回收的通知无法执行重新打开会话的点击回调，因此 shell 会引用每个通知，直到它上报点击或关闭。该持有是有界的，因为平台未必为用户忽略的 toast 上报关闭事件；进程离开时统一释放。

**Windows toast 身份取自安装器写入的值。** NSIS 安装器把 electron-builder 的 `appId` 作为 AppUserModelID 写入它创建的快捷方式，因此打包把同一值以 `dshAppId`（两份 builder 配置中的 `extraMetadata`）写入打包后的 manifest，shell 在打开任何窗口之前用 `app.setAppUserModelId` 发布它。未打包运行不发布任何身份，除非 `DSH_DESKTOP_APP_ID` 指定。

## 考虑过的替代方案

由 Host 上报被否决：Host 没有通知界面，要触达 shell 需要新增 Host 到 shell 的协议，并为点击回传会话导航再建一条通道。由 `approval/request` 与 `user-questions/request` 瀑布通知被否决，因为它依赖监听器注册顺序。禁用时完全不接收上报、仅在前台时抑制被否决，因为那样打开设置后必须重新加载才生效。为转发的 Host 事件增加持久化 `turn/end` 原因被否决，因为它的改动更大——需要新增线上接口、生成的 Cordis 目录条目和双语文档，而中性的“任务已结束”文案已经如实覆盖该区别——并记录为后续可区分“被取消”与“已完成”的改进项。

## 结果

切走的用户会在任务停止、失败或需要回答时收到提示，并可点击通知直达该会话。在 Windows 和 Linux 上，关闭窗口默认不再结束工作，因此托盘成为返回窗口的入口；设置界面随时可恢复询问。通知只包含按语言提供的状态文案和有界长度的会话显示标题，别无其他；由于会话没有标题时客户端用首条用户消息推导它，而 Windows 可以在锁屏展示通知，该标题就是用户应当预期“无需解锁即可读到”的唯一会话内容。又因为 Host 不会为断开的连接发布状态事件，断线永远不会被上报为任务结束。在持久化轮次结束原因到达客户端之前，被取消的运行会显示为“任务已结束”。

## 验证

单元与集成测试覆盖上报标识规则（运行区间、失败抑制、子代理完成与失败、会话列表之外的已公告子代理、渲染器实例标识、请求键）、shell 的校验、去重、前台、已禁用与不支持路径、通知持有及其上限、关闭询问及其记住的答案、托盘菜单及其拒绝路径与销毁、设置界面的双向交互（含被拒绝的更改）、激活点击，以及 AppUserModelID 解析与“在打开任何窗口之前发布”的发布点。`pnpm run verify-client-ui-i18n` 覆盖文案，桌面测试套件覆盖 Electron 接线。toast 身份、专注助手行为，以及已安装快捷方式的 AppUserModelID 需要 Windows 上的已安装构建，此处明确未验证。
