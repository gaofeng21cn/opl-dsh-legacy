# Agent Note: 派发任务的反馈回路与唤醒接缝

Status: implemented

[English](2026-09-22-dispatched-task-feedback-and-wake-seam.md) | 中文

## Problem

把工作交给 DSH 会话的派活方，没有任何持久方式来得知工作已结束。`session.wait` 能报告那些持久事实，但只对愿意阻塞在单个会话上的调用方有效；长任务需要一份能挺过派活方自身重启的登记表，而且完成通知要送达"派活的那个会话"，而不是一个派活方必须一直养着的进程。

这条回路的前半段对于"如何从外部进程触达 Codex 会话"也没有诚实答案，因此唤醒传输很容易被伪造：另起一个 `codex resume` 进程、打开 `codex://` 链接、写一个文件、弹一个桌面 toast，看上去都像进展，但没有一个真的唤醒了发起派活的那个会话。

## Decision

新增 `@deepseek-ai/dsh-api-task-feedback`：一张以调用方 id 为键的任务登记表、一个无模型参与的监听器，以及一个通知 outbox，统一落在 `task_feedback` 存储域中。

- **状态区分了派活方会区别对待的事实。** `queued` 与 `accepted` 的差别在于本 Host 是否已能看到绑定的会话；`disconnected` 永不结算任务，因为"观测不到"不等于"失败"，而在暂时断线上重派会让同一份工作跑两遍；`cancelled` 只保留给会话自己记录为中止的轮次。本[结果边界记录](../bug-fix/2026-09-23-control-recovery-outcome-boundaries.zh.md)扩展了这些状态与续做接缝：未经验证的完成字段让泄漏语法的轮次不会被读成业务成功，手动停止时的收手会撤回已排队的自动续做。
- **任务由会话自身的持久事件结算。** 监听器订阅 `session/event`，用循环写入的同一套 `TurnEndReason` 词表报告 `turn/end`，并对两类暂停报告 `waiting_approval` 与 `waiting_input`。它从不替人作答审批。
- **默认只通知结果与暂停状态。** `completed`、`failed`、`waiting_approval`、`waiting_input` 是默认 `notifyStates`；`queued`、`accepted`、`running`、`cancelled`、`disconnected` 只被观测，除非部署显式加入，否则不消耗付费模型轮次。等待类投递的 id 带上其稳定的暂停键——审批为决定事件位置，结构化提问为游标加所问问题 id——因此同一日志游标处两次不同的暂停会分别通知，而重放请求不会。
- **通知是"至少一次 + 带所有者的领取幂等"。** 重试有界且为封顶指数退避。重试耗尽的投递保持待发且未确认，而不是被丢弃。升级会退役当前策略不再通知的待发投递，因此旧版本入队的 `running` 条目不会被重投；退役不等于确认。消费有自己独立的持久台账：`receive` 领取投递并回答审查、恢复、忙碌或跳过，`consume` 结束领取，`receipts` 列出重启后的接收方仍欠什么。receipt 带 `ownerId`、`claimEpoch` 与 `leaseExpiresAt`：所有者租约仍有效时，以不同 id 到来的消费者得到 `busy`；租约过期的领取以新代次被回收；`consume` 拒绝调用方已不再持有的代次。稳定 consumer id 可立即恢复自己的领取，这正是重启后的接收方在不与在工作者相撞的前提下取回审查的方式。
- **投递阶段是彼此独立的断言，而消费另有自己的台账。** `enqueued`、`delivered`、`received`、`review-started` 是四个不同事实；传输层接手只证明 `delivered`，仅此而已。接收方通过 `taskFeedback.receive` 领取、通过带领取代次的 `consume` 结束（出厂控制桥暴露为 `opl-dsh-control receive|receipts|consume`）；`ack` 仍是更底层的阶段记录。没有任何发送方代码写入 `received`、`review-started` 或 receipt。
- **一种精确的协议错误可获得有界的自动续做。** 只有 `turn/end` 的结构化 `LlmFailure` 是 HTTP 400 invalid request、且明确说明 reasoning_text must be passed back 时才算合格；仅仅提到该 token 的文本不算。接收方调用一个确定性操作 `resumeFailed`（`resume-failed`），它以接收方的 consumer 身份领取投递——若省略该 id，则延续该投递上已记录的领取，因此通知自身的"先领取后恢复"两步不会互相挡住——确认失败轮次仍是目标，并在原会话提交一条持久用户指令，或报告 `not-applicable`、`superseded`、`running`、`busy`、`budget-exhausted`。指令带确定性 request id，因此重复通知会重放同一条指令，而 receipt 标记写入丢失后，若指令已出现在会话日志或活动 inbox 中，也会幂等重放。已准入但未观测到提交的尝试在再次尝试前会重新执行取代检查，因此操作者手动继续之后的重放会收手，而不是追加过时的自动续做；后续任务只在指令被接受后才登记，因此提交失败的尝试不会把该手动轮次绑到任何任务上。准入还会持久化提交该指令时的游标与结束轮次基线，后续任务绑定的是消费了它自己那条指令的轮次，因此登记晚于该轮次时——任务写入丢失或进程重启——会依据会话已记录的事实（已完成、已再次失败、已暂停等待审批或仍在运行）补偿结算，而不是把最后结束的轮次当成续做结果。receipt 写入是唯一的准入提交点，也是预算台账：计数由按原始任务为键的 receipt 派生，并以 `parentTaskId`/`rootTaskId` 被任何重试共享，任务记录写入丢失、重启或重放投递都不会重复计数。带父级关联的后续任务跟踪续做轮次，并在其完成、再次失败或暂停时通知同一目标；旧的 `failed` 记录绝不被改写。操作者停止时被撤回的已排队指令会让该尝试收手，这次撤回与它所发布的 `cancelled` 尝试记录由[结果边界记录](../bug-fix/2026-09-23-control-recovery-outcome-boundaries.zh.md)负责。
- **唤醒传输是一条由 Config 驱动、带诚实默认值的接缝。** 出厂默认是 `unconnected`，拒绝一切投递并报告 `not-connected`，绝不断言某台机器的事实。部署设置 `wakeTransport`、`wakeExecution`、`wakeExecutable`、`wakeDistro`；适配器以参数数组启动，带 `windowsHide`、有界超时与取消，`wake()` 用同一条入口探测 `codex --version`，在可执行文件确实运行时报告 `executable-started`——绝不报告目标线程或投递通道已连通。
- **投递靠调度，而非轮询。** 一条入队通知只武装一个唤醒点；任意时刻最多一个唤醒点与一个投递 pass，pass 会先等待监听器的写入再读取 outbox；卸载会取消唤醒点并等待已在运行的 pass。重启会为 outbox 仍欠的内容武装一次恢复 pass，并为尚未落盘通知的应通知状态补入队，从而修复任务写入与 outbox 写入之间的崩溃。接收方一经领取，发送方即停止重试，此后是 receipts 台账而非 outbox 成为重启后接收方的读取点。
- **恢复读取会话已记录的内容。** 若任务的轮次在 Host 停机期间结束，恢复时从 `sessionWait` 投影结算，而不是等待一个已经发生过的事件。续做尝试由记录它自己那条指令的轮次结算，绝不依据最后结束的轮次，因此其后发生的人工轮次不会被当成续做结果。登记时未绑定轮次（因指令在任何轮次认领之前被记录而呈现为 accepted 且 `turn: null`）的尝试任务，会在会话恢复时按该指令重新绑定，两种附着顺序都成立：会话已附着时由恢复遍历处理，会话稍后附着时由 `session/created` 补偿处理。本 Host 启动之后才恢复或附着的会话在其 `session/created` 边上补偿，因为带 seed 的会话不会为其载入的历史逐条发布事件；具名轮次按轮次号匹配，未具名轮次忽略登记时已在日志上的那次结束。

## Consequences

派活方可以重启而不丢任务、不丢通知，接收端也能安全消费重复通知。整条回路不依赖模型：不会为了盯住一个轮次而消耗另一个轮次，纯进度的 `running` 迁移一个轮次也不消耗。

有两个事实被显式保留，而不是被粉饰。其一，触达 Codex 会话仍需要部署自己指定传输：出厂默认拒绝投递，只说明未配置传输，绝不断言某台机器的 daemon、套接字或状态存储。因此适配器要求显式给出可执行文件、执行方式与发行版，绝不假设其中任何一项；其 `codex --version` 探测只报告可执行文件已启动，而不是目标线程或投递通道已连通。其二，只有接收方自己说"已开始"，审查才算开始：传输层入队或 `wake()` 探测绝不会被报告为 `received` 或 `review-started`，由接收方的持久领取决定审查是否运行，人类未作答的审批也保持可见，而不会被自动作答。

第三个事实同样被显式保留：自动续做是一次真实的新用户轮次，而不是隐形重试。续做请求保持会话原有的模型选择与思考状态，不伪造缺失的思考、不删除历史、也不重新执行已提交的工具。由于持久预算是有限的，最坏情况也只是有界次数的额外付费轮次；预算耗尽会报告给接收方而不是继续重试，该精确条件之外的一切失败都走正常审查。

## Alternatives considered

- **由协调器进程轮询 `session.wait`。** 作为主机制被否决：每个任务都要一个阻塞的调用者，它会随派活方一起死掉，而且无法报告"没人等待时轮次已结束"的任务。对于愿意阻塞在单个会话上的调用方，`session.wait` 仍是正确选择。
- **为被弃置的询问追加一条 `approval/decided`。** 被否决：本服务绝不能替人作答审批，而合成决定在审计轨迹中与人类决定无法区分。改为在读取模型上把询问限定到它所属的轮次。
- **会话离开本 Host 时把任务标为失败。** 被否决：暂时断线会被当成结果，并诱发一次会把工作跑两遍的重派。状态是 `disconnected`，任务保留位置。
- **为"新起一个 codex 进程"实现唤醒适配器。** 被否决：带着同一段会话历史的新进程并不是派活的那个会话，把它称作唤醒是对事实的误报。
- **硬编码 WSL 发行版或 Codex 安装路径。** 被否决：这会让构建绑定到某台机器，并把配置常量伪装成通道已连通。入口属于 Config，且由 `wake()` 实际探测。

## Testing

`packages/api/task-feedback/tests/task-feedback.host.spec.ts` 覆盖完成、失败、取消、审批与提问暂停、重复事件、任务隔离、默认通知策略、同一日志游标处两次不同暂停、旧 `running` 投递退役、唤醒配置错误、事件后无需显式 flush 的自动投递、封顶退避、卸载、并发 flush 与调度器竞争、入队写入仍在途时启动的 pass、重启后的自动补发、会话不可达、接收端不可达、有界重试与确认丢失——另外还有消费台账（重复消息、确认丢失、跨重启的中断领取、并发领取、租约到期后的接管、过期所有者被拒）、有界自动续做（精确 reasoning_text 条件及其近似反例、被更新的轮次/排队消息/取消取代、通知在同一 consumer 身份下的"先领取后恢复"协议、手动轮次后拒绝过时的已准入续做、两次续做写入边界下同一次准入只计一次、跨尝试与重启的持久预算、重试血缘、崩溃后的提交重放、续做轮次的反馈）、服务恢复之后才附着的会话、登记之前就已结束的轮次、以及 outbox 写入未落盘的通知。全部确定性、无 key、无模型，并使用模拟接收会话。`tests/task-feedback.controller.host.spec.ts` 让续做跑在生产 `SessionCommandController` 的 prompt 路径上，搭配真实 Agent 注册表、会话日志与 Inbox，仅替换外部模型选择与传输，覆盖真实准入与排队行为、提交重放、手动轮次后收手、以及"指令已入队但 receipt 标记写入丢失"的恢复。`tests/task-feedback.resume-tracking.host.spec.ts` 保留延迟登记回归：后续任务写入丢失，等到重放登记该任务时续做轮次已完成、已再次失败、已暂停等待审批或仍在运行，或其后已有一个人工轮次结束；每个用例都断言绑定本身，最后结束的轮次无法冒充续做结果。它还保留基于持久 JSON 根目录的冷恢复回归：登记时未绑定轮次的尝试任务，在服务先于保存的会话恢复时、以及在服务恢复时会话已附着时，都会从恢复的历史中补绑定；覆盖其后的人工轮次、仍在运行的续做轮次，以及第二次恢复不得重复通知。`tests/task-feedback.loop.host.spec.ts` 让该流程跑在真实 Agent loop 上：生产 `SessionCommandController` 把指令排入真实 Inbox，真实轮次认领、记录并跑完该指令；只替换模型传输。`tests/independent-review.host.spec.ts` 保留并发与确认竞态回归；`tests/wake.host.spec.ts` 用真实 Node 可执行文件运行有界进程执行器、参数数组与探测；`tests/task-feedback.loader.spec.ts` 通过 Loader 与 Include、基于真实存储、会话与投影提供者启动真实插件，并覆盖"保存的会话在服务恢复之后才附着"的重启顺序。
