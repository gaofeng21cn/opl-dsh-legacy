# Agent Note: dispatched-task feedback with a wake seam

Status: implemented

English | [中文](2026-09-22-dispatched-task-feedback-and-wake-seam.zh.md)

## Problem

A dispatcher that hands work to a DSH Session has no durable way to learn that the work settled. `session.wait` reports the durable facts, but only to a caller willing to block on one Session; a long task needs a registry that survives the dispatcher's own restarts, and the completion has to reach the Session that dispatched the work rather than a process the dispatcher has to keep alive.

The first half of that loop also had no honest answer for reaching a Codex Session from an external process, so a wake transport could easily be faked: a new `codex resume` process, an opened `codex://` link, a written file, or a desktop toast all look like progress while none of them wakes the Session that asked for the work.

## Decision

Add `@deepseek-ai/dsh-api-task-feedback`: a caller-keyed task registry, a watcher with no model involvement, and a notification outbox, all in the `task_feedback` storage domain.

- **States separate the facts a dispatcher acts on differently.** `queued` and `accepted` differ by whether this Host can already see the bound Session; `disconnected` never settles a task, because an unobservable Session is not a failed one and re-dispatching on a transient disconnect would run the work twice; `cancelled` is reserved for a turn the Session itself recorded as aborted. The [outcome-boundary note](../bug-fix/2026-09-23-control-recovery-outcome-boundaries.md) extends these states and the resume seam: an unverified-completion field keeps a leaked-syntax turn from reading as a business success, and a manual-stop stand-down withdraws a queued automatic resume.
- **A task settles on the Session's own durable events.** The watcher subscribes to `session/event` and reports `turn/end` through the same `TurnEndReason` vocabulary the loop writes, plus `waiting_approval` and `waiting_input` for the two pauses. It never answers an approval.
- **Only outcome and pause states notify by default.** `completed`, `failed`, `waiting_approval`, and `waiting_input` are the default `notifyStates`; `queued`, `accepted`, `running`, `cancelled`, and `disconnected` are observed but spend no paid model turn unless a deployment adds them. A waiting delivery's id carries its stable pause key — the deciding event position for an approval, the cursor plus the asked question ids for a structured question — so two distinct pauses at one log cursor notify separately while a replayed request does not.
- **Notifications are at-least-once with an idempotent, owned claim.** Retries are bounded with a capped exponential delay. An exhausted delivery stays pending and unacknowledged instead of being dropped. An upgrade retires pending deliveries whose state the current policy no longer notifies, so a `running` entry an older build enqueued is not re-sent; retirement is not an acknowledgment. Consumption has its own durable ledger: `receive` claims a delivery and answers review, resume, busy, or skip, `consume` finishes the claim, and `receipts` lists what a restarted receiver still owes. A receipt carries `ownerId`, `claimEpoch`, and `leaseExpiresAt`: a consumer that presents a different id while the owner's lease is live is answered `busy`, a claim whose lease expired is reclaimed under a new generation, and `consume` rejects a generation the caller no longer holds. A stable consumer id resumes its own claim immediately, which is how a restarted receiver takes its review back without racing a working one.
- **Delivery stages are separate claims, and consumption has its own ledger.** `enqueued`, `delivered`, `received`, and `review-started` are four different facts; a transport accepting a handoff proves `delivered` and nothing else. The receiver claims through `taskFeedback.receive` and finishes through `consume` with the claim's generation, exposed as `opl-dsh-control receive|receipts|consume`; `ack` remains the lower-level stage record. No sender code ever writes `received`, `review-started`, or a receipt.
- **One exact protocol failure gets a bounded automatic resume.** A `turn/end` whose structured `LlmFailure` is an HTTP 400 invalid request stating that reasoning_text must be passed back is the only eligible failure; text that merely mentions the token is not. The receiver calls one deterministic operation, `resumeFailed` (`resume-failed`), which claims the delivery under the receiver's consumer identity — or under the claim already recorded for that delivery when the id is omitted, so the notification's own claim-then-recover steps cannot block each other — verifies the failed turn is still the target, and submits one persisted user instruction in the original Session, or reports `not-applicable`, `superseded`, `running`, `busy`, or `budget-exhausted`. The instruction carries a deterministic request id, so a duplicate notification replays the same instruction, and an instruction already present in the Session log or live inbox replays idempotently after a lost receipt flag write. An admitted attempt whose submission was never observed re-runs the supersession checks before trying again, so a replay after a manual continuation stands down instead of appending a stale automatic one, and the follow-up task is registered only once the instruction is accepted so a failed submission binds no task to that manual turn. The admission persists the cursor and turn-end baseline it was submitted at, and the follow-up task binds to the turn that consumed its own instruction, so a registration delayed past that turn — a lost task write or a restart — compensates from the Session's recorded facts (completed, failed again, paused for approval, or still open) instead of reading the last turn end as the resume. The receipt write is the single admission commit point and the budget ledger: the count is derived from receipts keyed by the original task, shared by any retry registered with `parentTaskId`/`rootTaskId`, and never double-counted by a lost task-record write, a restart, or a replayed delivery. A follow-up task, linked by parent, tracks the resumed turn and notifies the same target when it completes, fails again, or pauses; the old `failed` record is never rewritten. A queued instruction the operator's stop withdraws stands the attempt down, which the [outcome-boundary note](../bug-fix/2026-09-23-control-recovery-outcome-boundaries.md) owns together with the `cancelled` attempt record it publishes.
- **The wake transport is a Config-driven seam with an honest default.** The shipped default is `unconnected`, which refuses every delivery and reports `not-connected` without asserting anything about a particular machine. A deployment sets `wakeTransport`, `wakeExecution`, `wakeExecutable`, and `wakeDistro`; the adapter launches an argv array with `windowsHide`, a bounded deadline, and cancellation, and `wake()` probes `codex --version` through that same entry and reports `executable-started` when the executable ran — never that a target thread or a delivery channel is connected.
- **Delivery is scheduled, not polled for.** A queued notification arms one wake-up; at most one wake-up and one delivery pass exist at a time, the pass waits for the watcher's writes before it reads the outbox, and disposal cancels the wake-up and awaits the pass already running. A restart arms one recovery pass for whatever the outbox still owes and re-enqueues a notifying state whose delivery never landed, which repairs the crash between the task write and the outbox write. Once a receiver claims a delivery the sender stops retrying it, so the receipts ledger, not the outbox, is what a restarted receiver reads.
- **Recovery reads what the Session recorded.** A task whose turn ended while the Host was down settles from the `sessionWait` projection instead of waiting for an event that already happened. A resume attempt is settled through the turn its own instruction was recorded in, never by the last turn to end, so a manual turn that ran afterwards cannot be read as the resume. An attempt task whose registration landed without a turn — accepted with `turn: null` because its instruction was recorded before a turn claimed it — is rebound from that instruction when the Session is restored, on either attachment order: the recovery pass when the Session is already attached, or the `session/created` reconcile when it attaches later. A Session restored or attached after this Host started is reconciled on its `session/created` edge, because a seeded Session publishes no per-event feed for the history it loads with; a named turn matches by number, and an unnamed one ignores the end already on the log at registration.

## Consequences

The dispatcher can restart without losing a task or a notification, and a receiver can consume a repeated notification safely. Nothing about the loop depends on a model: no turn is spent watching another turn, and a progress-only `running` transition spends no turn at all.

Two facts stay visible rather than being papered over. First, reaching a Codex Session still needs a transport the deployment names itself: the shipped default refuses delivery and explains only that no transport is configured, without asserting anything about a particular machine's daemon, socket, or state store. The adapter therefore takes an explicit executable, execution mode, and distribution rather than assuming any of them, and its `codex --version` probe reports only that the executable started — not that a target thread or a delivery channel is connected. Second, only the receiving side can say a review started: a transport enqueue or a `wake()` probe is never reported as `received` or `review-started`, the receiver's durable claim decides whether a review runs, and an unanswered approval stays visible rather than being auto-answered.

A third fact is explicit rather than hidden: the automatic resume is a new user turn, not an invisible retry. The resumed request keeps the Session's existing model selection and thinking state, does not fabricate the missing reasoning, does not delete history, and does not re-execute committed tools. Because the durable budget is finite and persisted, the worst case is a bounded number of extra paid turns; an exhausted budget is reported to the receiver instead of being retried, and every failure outside the one exact condition follows normal review.

## Alternatives considered

- **Polling `session.wait` from the coordinator process.** Rejected as the primary mechanism: it needs one blocked caller per task, it dies with the dispatcher, and it cannot report a task whose turn ended while nobody was waiting. `session.wait` remains the right call for a caller that is willing to block on one Session.
- **Appending an `approval/decided` event for an abandoned ask.** Rejected: this service must never answer an approval, and a synthetic decision would be indistinguishable from a human's in the audit trail. The read model scopes the ask to its turn instead.
- **Marking a task failed when its Session leaves this Host.** Rejected: a transient disconnect would look like an outcome and invite a re-dispatch that runs the work twice. The state is `disconnected`, and the task keeps its place.
- **Shipping a wake adapter for a new `codex` process.** Rejected: a fresh process with the same conversation history is not the Session that dispatched the work, and calling it a wake would misreport what happened.
- **Hardcoding a WSL distribution or Codex install path.** Rejected: it makes the build machine-specific and turns a configured constant into a false claim that the delivery channel is connected. The entry is Config, and `wake()` probes it.

## Testing

`packages/api/task-feedback/tests/task-feedback.host.spec.ts` covers completion, failure, cancellation, approval and question pauses, duplicate events, task isolation, the default notification policy, two distinct pauses at one log cursor, legacy `running` retirement, wake misconfiguration, automatic delivery after an event with no explicit flush call, capped backoff, disposal, concurrent flushes racing the scheduler, a pass that starts while the enqueue write is still in flight, restart recovery with automatic re-send, an unreachable Session, an unreachable receiver, bounded retries, and acknowledgment loss — plus the consumption ledger (duplicate messages, a lost acknowledgment, an interrupted claim across a restart, concurrent claims, takeover after lease expiry, and stale-owner rejection), the bounded automatic resume (the exact reasoning_text condition and its near misses, supersession by a newer turn, queued message, or cancellation, the notification's claim-then-recover protocol under one consumer identity, rejection of a stale admitted continuation after a manual turn, one admission counted once across both resume write boundaries, a persisted budget across attempts and a restart, retry lineage, submission replay after a crash, and feedback on the resumed turn), a Session attached after the service recovered, a turn that ended before registration, and a notifying state whose outbox write never landed. Every case is deterministic, with no key, no model, and a simulated receiving Session. `tests/task-feedback.controller.host.spec.ts` runs the resume over the production `SessionCommandController` prompt path with the real Agent registry, Session log, and Inbox, replacing only the external model selection and transport, covering real admission and requeue behavior, submission replay, stand-down after a manual turn, and recovery of a queued instruction whose receipt flag write was lost. `tests/task-feedback.resume-tracking.host.spec.ts` keeps the delayed-registration regression: the follow-up task write is lost, and by the time the replay registers the task the resumed turn has already completed, failed again, paused for approval, or is still open, or a manual turn ended after it; each case asserts the binding, so the last turn end cannot stand in for the resume. It also keeps the cold-recovery regression over a durable JSON root: a task registered without its turn is rebound from restored history when the service recovers before the saved Session attaches and when the Session is already attached as the service recovers, including a later manual turn, a still-open resumed turn, and a second recovery that must not notify again. `tests/task-feedback.loop.host.spec.ts` runs that flow over the real Agent loop, with the production `SessionCommandController` queueing into the real Inbox and a real turn claiming, recording, and completing the instruction; only the model transport is scripted. `tests/independent-review.host.spec.ts` keeps the concurrency and acknowledgment-race regressions; `tests/wake.host.spec.ts` runs the bounded process runner, the argv arrays, and the probe against the real Node executable; `tests/task-feedback.loader.spec.ts` boots the real plugin through Loader and Include over the real storage, Session, and projection providers, including the restart order where the saved Session attaches only after the service recovered.
